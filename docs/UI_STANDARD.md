# Purpose
































































This is the single cross-domain UI/interaction owner for Freshwater Fishing Companion. It consolidates the former `NAVIGATION-PAGE-STANDARD.md`, `CARD_PAGE_STANDARD.md`, `DETAIL-PAGE-STANDARD.md`, and the UI-specific portions of `STYLE_GUIDE.md`.
































































Domain workstreams may define justified local behavior, but they must not silently create a competing site-wide standard.
































































# General Interface Principles
































































The interface should be clean, calm, beginner friendly, fast, field-usable, mobile-first, and readable outdoors.
































































- Prefer completing a task in the current context over adding an intermediate page with no distinct value.
- Keep common field workflows within approximately three intentional interactions from a relevant entry point when practical.
- Avoid visual clutter and duplicated instructional content.
- Anything that looks actionable must either work or clearly communicate that it is unavailable.
- Use one canonical data/relationship owner; UI convenience does not justify duplicate semantic storage.
































































# Forest Journal and Theme Boundary
































































Forest Journal is the only production-supported Version 1 theme and the current visual reference baseline.
































































UD-11 Appearance defines separate **Theme** and **Color Scheme** concepts, but they form one coordinated Appearance capability. Both are device-local settings. A production theme declares the System/Light/Dark variants it supports, and the interface must not expose an unsupported theme/scheme combination. **System** follows the device/browser light-dark preference using only validated variants supported by the selected theme.
































































Light/Dark must select intentionally designed, theme-specific variants rather than apply a generic brightness filter or automatic darkening/lightening transformation. A dark-oriented theme does not need to become darker to qualify as its Dark variant. In particular, Forest Journal Dark should preserve the current readable visual range unless deliberate design work demonstrates a better validated treatment; do not automatically darken its backgrounds, cards, borders, text, or media. A Forest Journal Light variant must be deliberately designed and validated before it can be exposed, and System must never switch into an untested/generated variant.
































































Only production-approved and validated themes may appear in the Theme selector. Forest Copper, Forest Gold, and Legacy Dark remain deferred/inactive candidates; they are not production themes, do not require current component parity, and are outside the production validation matrix until explicitly promoted through implementation and validation. The final Version 1 supported-theme set remains open and no arbitrary minimum theme count is required.
































































Shared layout, components, interaction, accessibility, and responsive behavior should remain centralized where practical. Production theme implementations should primarily vary design tokens and bounded intentional overrides rather than duplicate application structure.
































































The reference-media surface `#f4f0e8` / RGB `244, 240, 232` is a cross-theme invariant. Future themes must remain visually compatible with it rather than recolor that media surface.
































































# Shared Field-Guide Presentation
































































Reference and instructional pages should share recognizable information hierarchy, spacing, label conventions, media surfaces, contextual actions, related-knowledge patterns, navigation behavior, and mobile readability.
































































Do **not** force Fish photos, Rig diagrams, Tackle illustrations, Knot instructional media, and other domain media into one technical format; `MEDIA_GUIDE.md` owns media-specific rules.
































































## Guide-Family Component Baseline
































































Fish Guide is the starting Guide-family design baseline, but existing Fish presentation is not automatically the final standard. Fish earns baseline status through a deliberate component-by-component and element-by-element review. Each recurring element is reviewed, approved, implemented when change is required, and validated before its treatment is carried into later Guides.
































































The Fish baseline review must separately consider, where applicable:
































































- Guide identity and introductory framing;
- Search controls and scoped-search behavior;
- workflow/task entry cards and collection/browse cards;
- shared card shell geometry plus card-specific internal content;
- titles, eyebrows, labels, supporting text, metadata, media framing, chips, links, and actions;
- ordinary-information, workflow/action, warning/safety, readiness/status, and other semantically distinct states;
- internal-navigation and related-knowledge treatments;
- default, hover, focus, pressed/active, selected, disabled/unavailable, and touch behavior; and
- mobile, intermediate, standard-desktop, and wide-desktop layout behavior.
































































Equivalent elements in Knots Guide, Tackle Guide, Technique Guide, and Rig Guide should start from the approved Fish treatment and differ only when domain semantics or content structure justify a deliberate exception. Fish-specific structures such as scientific identity fields, anatomical identification, pairwise Fish comparison, species framing, and Fish-to-Rig guidance do not become universal Guide requirements merely because Fish is the baseline.
































































Guide/domain identity styling must remain conceptually separate from semantic/card-state styling. **Guide pages and Guide subpages do not receive a fixed Guide-specific color assignment.** Guide identity should come from content, headings, imagery, restrained motifs/graphics, and domain-appropriate information structure rather than making every Fish, Knot, Tackle, Technique, or Rig surface one assigned color. Equivalent internal-knowledge navigation should converge on one shared interaction treatment rather than acquiring unrelated domain-specific decoration. Exact visual implementation remains subject to the element-level review gates.
































































Guide-specific lightweight motifs or decorative graphics may be evaluated during the Fish baseline work, especially on Guide identity, landing, and browse surfaces, but they remain subordinate to content and must not become mandatory decoration inside dense detail/reference cards.
































































A Fish treatment becomes a reusable Guide-family baseline only after the relevant section has passed its approval gate and applicable desktop/mobile validation.
































































# Landing / Navigation Page Hierarchy
































































Fish Guide is the active Guide-family landing-page baseline under FCC 48. Gate 152 is CLOSED / PASS / refinement allowed through checkpoints 152.1-152.8. R1 browser review resolved Fish desktop Search width in favor of a constrained width approximately equal to two cards in the three-column Guide browse grid, and R2 browser review resolves Compare Similar Fish in favor of the normal grid-position width rather than row spanning. These refinements do not reopen the approved landing hierarchy, interaction model, or responsive baseline. Where applicable, a Guide landing page uses:
































































1. **Guide identity** — a compact heading/introduction block with concise purpose text and optional restrained domain motif; do not turn mobile Guide identity into a large marketing hero;
2. **Search** — the first functional navigation element when the Guide is searchable;
3. **special/workflow navigation** — only when it materially improves a real task;
4. **Browse/collection framing** — a concise section heading followed by category/collection cards. Supporting copy is optional and should be omitted when the cards are already self-explanatory.
































































Permanent principle:
































































> Landing pages navigate to useful groups; browse/detail pages display individual records.
































































Do not let a landing page grow linearly with record count when useful collections can preserve a concise hierarchy.
































































# Search Interaction and Scope
































































Search uses one shared interaction pattern across searchable sections/subsets:
































































- inline search at the relevant section entry point;
- domain search covers that implemented domain library;
- subset/browse search searches **only** records eligible for the selected subset;
- **Guide-family Search is live by default and does not display a visible Search button.** Typing performs the search/filter immediately; Enter/mobile Search submission may continue to trigger the same behavior internally. A Guide may retain an explicit submit control only when a separately approved functional reason requires one;
- use concise, scope-clear labeling such as `Search Fish` rather than unnecessary `Search all ...` wording when the page scope is already obvious;
- use concise scope helper text such as `Search by common name, alias, or group.`; keep placeholder examples optional and validate any maintained examples against the active scope;
- show a one-click `×` clear control whenever the field contains text; present it as a small visible chip/button with a comfortably sized touch target rather than a loose symbol;
- accessible clear label = `Clear search`;
- shared Guide search styling uses the shared interface/theme treatment and must not depend on a fixed Guide-specific color. Domain-specific color may appear only where it has separately approved semantic meaning;
- clearing restores the default/unfiltered state for the **current scope** and may retain focus in the same search field;
- do not auto-focus Search merely because a page/collection renders, especially on mobile;
- helper text/examples/empty states must accurately describe the active scope;
- manually maintained examples must be validated against the exact eligible collection or replaced by scope-descriptive wording;
- search never silently broadens upward from a subset to a parent/global scope;
- on the Fish landing page, mobile/intermediate Search uses the available width. On desktop, constrain the Fish Search surface to approximately the width of two cards in the three-column Guide browse grid; this is the approved Fish baseline, not automatically a universal width for every Guide.
































































Conceptual hierarchy:
































































```text
Global Search (future)
→ all implemented searchable domains
































































Domain Search
→ all active records in one domain
































































Collection / Subset Search
→ only records eligible for the selected collection
































































Related-Knowledge Search (future, only if useful)
→ only entities reachable through the approved relationship set
```
































































Search is relevance-first. Exact canonical names/approved aliases and strong identity signals outrank weaker metadata. Browse lists may remain alphabetical or use an explicitly approved curated order.
































































# Special / Task Navigation
































































Special navigation is optional and appears **after Search and before collection cards** when it materially helps a beginner accomplish a task without first knowing a canonical record name/category.
































































- Keep task navigation compact and task-oriented.
- Do not duplicate the same destination at the same hierarchy under several labels. For a single featured workflow card, prefer letting the card carry its own title, concise explanation, and action rather than repeating the same heading/explanation immediately above it.
- A task may open a workflow, curated collection, or appropriate destination without exposing that implementation distinction to the user.
- Priority belongs to individual important tasks, not automatically to an entire surrounding section.
- A small eyebrow/label such as `Identification Tool` may be tested when it clarifies the kind of workflow, but it is not mandatory decoration.
- Do not force a single workflow card to span a wider desktop area merely because space exists. Fish R2 browser review approves **normal grid-position width** for Compare Similar Fish at intermediate/desktop widths; do not row-span that Fish workflow card absent a later concrete layout reason.
- Do not add a second large domain graphic inside a workflow card merely because the Guide identity block already uses restrained visual flair.
































































Current Knot examples: **Attach Line to a Reel** and **Tie On a Hook, Swivel, or Lure** are Important tasks; Connect Two Lines/Add a Leader and Make a Loop Connection are normal task cards.
































































# Card System
































































The Dashboard remains a visual reference for peer-choice card grids, but Guide browse cards may use a dedicated **Guide/reference-card variant** rather than copying the Dashboard card shell exactly. D048 applies to Dashboard, section landing, browse/category, collection, task, catalog, comparison, and other peer-card panels.
































































## Required shared treatment
































































1. Adjacent **standard** peer cards use differing accents from the approved shared palette rather than one repeated domain color. The same standard accent may repeat later in the sequence, but not on sequential standard cards.
2. **Special/workflow cards use a reserved standardized special-accent set. Standard cards in the same section must not use an accent currently reserved for those special cards.** If a section contains multiple special cards, more than one standardized special accent may be used so those special cards also avoid a same-same run. Exact special-accent assignments remain a theme/palette implementation decision until visually validated.
3. The card's left-edge accent, accent-coupled border/action/focus treatment, spacing, radius, proportions, and responsive behavior remain in the shared application family. **Do not use accent-tinted bloom, glow, or gradient wash across card surfaces.** Card surfaces use the normal neutral surface/elevation family; accent identity stays on edges, borders, actions, labels, and focus states. Guide browse cards may tune neutral border/depth subtly to read as reference-library cards without becoming a separate graphic-heavy design language.
4. Color rotation is deterministic/stable for a rendered order.
5. Guide/domain identity is not encoded as a fixed page/subpage color. Identity may appear through headings, imagery, restrained motifs, content structure, and other approved domain cues; standard peer-card accents still come from the shared multi-accent palette.
6. Primary/Core/Important hierarchy is additive to the shared card system rather than a separate design language.
7. Unavailable cards stay in the same visual family while removing misleading actionable affordances.
































































## Guide browse-card shell and internals
































































For the Fish landing baseline approved through checkpoint 152.6:
































































- keep a compact rounded rectangular shell; do not add large Fish graphics to every browse card;
- use the approved responsive browse baseline: **1 column below 640px, 2 columns from 640-899px, and 3 columns at 900px and above**. Wide desktop retains the centered readable application canvas rather than adding 4+ browse columns merely because viewport space exists;
- keep `All Fish` in the same standard outer shell as the other browse choices rather than styling it as a special workflow;
- keep short descriptive copy when it helps a beginner understand what the collection contains;
- retain an explicit action cue such as `Browse →` or `Compare →` even when the entire card is clickable/tappable; the cue explains what the card does and is not a separate competing destination;
- place the action cue on the same top row as the title when there is comfortable room; if the title/action pair no longer fits cleanly, move the entire action cue to a new line and **left-align it** rather than squeezing the title, shrinking text, or leaving the action stranded at the far edge;
- Fish R2 browser review approves the lighter **non-pill text-action** treatment for Fish landing/browse actions such as `Browse →` and `Compare →`. Treat this as the Fish baseline; promotion to unrelated domains still requires equivalent-element review;
- card accent identity remains attached to the card/rendered order as the grid reflows; breakpoint changes do not recalculate accents by visual column, and standard cards still must not consume reserved special/workflow accents;
- for approved landing navigation cards, the whole card remains the interactive control; hover treatment is restrained and applies only where hover is available; keyboard focus is clearly visible and not allowed to disappear into decorative accent treatment; pressed/touch feedback is subtle; actionable targets use the 48px minimum; a genuinely unavailable Compare entry is omitted rather than rendered as a misleading disabled action; reduced-motion preferences are respected;
- normal browse cards do not require extra eyebrows such as `Fish Group`.
































































Specialized card internals are allowed when content requires them (for example Compare Fish pair imagery, readiness state, compact relationship metadata). **A custom internal card renderer is not an exception to D048.**
































































### Guide browse/search result-card baseline
































































Fish Guide checkpoint 153.1 establishes the first result-card baseline for later Guide-family review:
































































- use one shared Fish result-card architecture across landing Search and collection Browse/Search;
- order Fish result-card content as **Category → Common Name + action cue → image → alias/Also called when present → short summary**;
- do not show scientific name or Family on the browse/search result card. Those remain detail/reference information;
- omit the alias row entirely when no approved alias exists; when present, place `Also called:` below the Fish image so optional alias data does not shift peer image alignment;
- keep the whole card actionable when detail exists and retain a lightweight `View Fish →` cue. At normal desktop result-card widths, Common Name and `View Fish →` share one deterministic heading row with the action held to the right; do not let individual desktop cards independently move the action to a second line;
- standard result cards use the shared rotating accent palette and must not repeat the same accent on sequential standard cards or consume a special/workflow accent reserved in that section;
- Fish browse/search uses the same live-search/no-visible-Search-button default as other Guide-family search surfaces; clearing restores the complete current collection;
- preserve the approved Fish ordering/search semantics: empty-query browse remains A-Z and typed Search remains relevance-ranked;
- mobile uses one result-card column; intermediate/tablet and full desktop use **two result-card columns maximum**. The three-column desktop candidate was rejected in R1 browser review because wider two-column cards better support Fish imagery, title/action fit, and scanability;
- breakpoint changes must not remove approved information or introduce horizontal scrolling.
































































Fish Guide checkpoint 153.2 closes the result-state and interaction baseline:
































































- Fish Guide landing Search shows no result count and no result-card grid while its query is empty; the landing page's Browse Fish navigation remains the empty-query discovery path;
- collection Browse/Search shows the complete current collection A-Z while its query is empty and may show the compact visible status `N fish`;
- active filtering uses the compact visible status `N fish found`;
- the normal no-match state is `No fish found. Try another search.` and remains distinct from the true collection/data-empty state `No fish are currently available in this collection.`;
- the clear `x` clears the full query in one action, immediately restores the correct empty-query state for that surface, retains or returns keyboard focus to Search, requires no submit/reload, and must not create an unnecessary scroll jump;
- result status uses polite assistive announcement behavior rather than assertive alerts; the clear control keeps the accessible name `Clear search`;
- the whole actionable result card remains one interactive target. `View Fish ->` is a visual cue, not a separately focusable nested control;
- hover feedback is restrained and does not replace the card's assigned accent. Keyboard `:focus-visible` is clearly visible around the whole card, pressed/touch feedback is subtle, and touch behavior never depends on hover;
- no scale/lift animation is required for result cards; reduced-motion support remains applicable;
- if detail is unavailable, render a genuinely non-interactive fallback without `View Fish ->`, pointer cursor, or hover/focus treatment that implies navigation;
- no dedicated persistent loading state is required for the current local/static Fish dataset. If a later implementation makes this surface asynchronous, loading treatment must be added deliberately rather than inferred from this omission.
































































Gate 153 is **CLOSED / PASS / refinement allowed** through checkpoints 153.1-153.2. R1/R2 browser review resolves the full-desktop density at **two Fish result-card columns maximum**; the three-column Fish result candidate is rejected for the approved baseline.
































































### Fish detail-page working baseline — checkpoint 154.1
































































Checkpoint 154.1 establishes the **Fish-first detail-page working direction** and remains refinement-allowed through implementation review. It does **not** yet promote one fixed detail layout across all Guides. Build and review Fish first, refine the exact mobile/desktop composition and disclosure-panel visual language against the real implementation, finalize Fish, and only then evaluate which successful equivalent-element treatments should become Guide-family standards.
































































The visible Fish detail hierarchy should preserve, where applicable: **Parent/Home → category → dominant common name → explicitly labeled subordinate scientific name → approved aliases when present → compact Family metadata → prominent primary Fish image → a visible beginner-oriented `How to Identify This Fish` overview**. The overview is primary detail content and should remain visible rather than being hidden behind a secondary control. This checkpoint defines the presentation requirement, not a new canonical Fish data field.
































































Supporting information may be grouped under a compact **ABOUT THIS FISH** treatment, especially on mobile. The current working set is **Key Identification Traits**, **Habitat & Water**, **Rigs to Start With**, and **Compare Similar Fish →**. Checkpoint 154.3 refines the first three rows into **independent expanders**: the complete labeled row is the control target, `▾` denotes collapsed, `▴` denotes expanded, each starts collapsed on initial Fish-detail entry, and opening one does not automatically close another. `ⓘ` is reserved for contextual/reference information about a specific concept and is not an expand/collapse cue. `→` continues to denote navigation/workflow. **How to Identify This Fish** remains visible core content outside the collapsible group.
































































Disclosure creates room to improve the internal presentation instead of merely hiding the old compact treatment. Pills/chips remain appropriate for short categorical values, while compact information rows, restrained icon/label treatments, or other space-aware structures may be tested for richer concepts and recommendations. Rigs should preserve recommendation structure such as priority, reason, and navigation rather than collapsing structured guidance into pills. Exact iconography, panel geometry, desktop arrangement, modal/bottom-sheet/inline behavior, and the final balance among chips, rows, or restrained tiles remain build-review decisions.
































































Material safety/handling cautions must not be hidden solely for compactness: when a Fish requires a meaningful warning before action, retain an appropriately visible warning/status cue even if the full explanation is disclosed. Guide/domain identity still does not receive a fixed Guide-specific page color.
































































### Fish identification-content structure — checkpoint 154.2
































































Checkpoint 154.2 is **APPROVED / refinement allowed**. The visible **How to Identify This Fish** overview uses the existing Fish `summary` as the quick-recognition layer; no new Fish schema field is introduced. The **Key Identification Traits** independent expander exposes the existing strongest-first `identificationTraits[]` as detailed species-owned recognition guidance, while **Compare Similar Fish →** remains the exclusive UI path for explicit look-alike/pairwise distinction content owned by `FISH_IDENTIFICATION_RELATIONSHIPS`.
































































The visible overview should normally remain one concise beginner-readable sentence centered on approximately 2–3 high-value observable clues. Detailed traits should remain short stacked statements/rows rather than being reduced to pills; they may use precise anatomical terms when useful, but wording should remain understandable to a new angler. Exact bullet/row styling and disclosure geometry remain implementation-review decisions.
































































Existing explicit cross-species wording inside some species-owned `identificationTraits[]` is a targeted semantic-cleanup requirement: preserve the approved Fish fact, rewrite the species-owned trait intrinsically where practical, and keep explicit “Fish A versus Fish B” wording in the identification-relationship owner. This checkpoint does not create an anatomy glossary or broader terminology system.
































### Fish Habitat & Water supporting-information structure — checkpoint 154.3
































Checkpoint 154.3 is **APPROVED / refinement allowed**. **Habitat & Water** is an independent ABOUT THIS FISH expander using the shared `▾` collapsed / `▴` expanded grammar. It starts collapsed on initial Fish-detail entry, the full labeled row toggles it, and its state is independent from **Key Identification Traits** and **Rigs to Start With**.
































Inside the expanded section, keep **Habitat** and **Common Waters** semantically separate. Habitat answers what physical environments the Fish commonly uses; Common Waters answers what kinds of waterbodies the Fish is commonly found in. Against the approved canonical Habitat target, render only applicable Habitat dimension groups: **Cover**, **Water Zone**, **Water Movement**, **Structure**, and **Bottom / Substrate**. Omit empty group headings. Keep waterbody types in their own simpler Common Waters group, including the approved `Creek / Stream` normalization when the later Fish migration lands.
































Short Habitat and waterbody values remain compact **clickable knowledge chips**. The entire chip is the contextual-information target and should be visibly distinguishable from passive labels through deliberate interactive surface/border treatment plus hover, focus-visible, and pressed states where applicable. A trailing `ⓘ` may reinforce that the chip opens explanatory/reference knowledge while preserving Fish context; the icon itself is not a separate nested target. Passive chips/labels must not inherit the same complete interactive treatment.
































Do not use Fish Habitat associations to imply preference strength, ranking, current conditions, or Recommendation suitability. The approved Habitat↔Condition and waterbody bridges establish environmental equivalence only. The UI should use neutral wording such as **Habitat** / **Common Waters**, not stronger unsupported labels such as Best Habitat or Preferred Conditions.
































Design against the already-approved canonical 13-concept Habitat target, but do not perform or imply the pending legacy `habitatTags[]` → canonical Fish↔Habitat migration at this design checkpoint. Exact spacing, wrapping, columns, animation, chip styling, and mobile/desktop disclosure geometry remain build-review refinements.
















### Fish Rigs to Start With supporting-information structure — checkpoint 154.4
















Checkpoint 154.4 is **APPROVED / refinement allowed**. **Rigs to Start With** remains an independent ABOUT THIS FISH expander using the shared `▾` collapsed / `▴` expanded grammar. Inside the expanded section, use compact structured recommendation rows rather than chips.
















Group recommendations as **Primary Choices** and **Alternatives**. Within each group, preserve an intentional **unnumbered descending presentation order** representing general-purpose beginner starting value for targeting that Fish. Do not display numeric ranks, scores, `#1`, Best badges, or other explicit ranking labels. This stable Fish Guide ordering is not a substitute for What Should I Throw contextual ranking and carries no current-condition, availability, legality, or user-tackle meaning.
















Each recommendation row shows the beginner-facing Rig/presentation name, the canonical Fish-specific guidance `reason`, and an explicit **View Rig →** navigation cue. The reason is substantive guidance and should be visible when the expander is open rather than discarded from presentation. Exact whole-row clickability remains a build-review decision; do not create nested competing targets.
















For Direct-Tie guidance, present the meaningful Lure/Bait identity itself — for example **Inline Spinner** or **Crankbait** — rather than exposing the internal **Direct-Tie Lure Setup** owner in the Fish-detail label. Preserve the underlying `rigId` + `lureBaitId` relationship and route to the corresponding Direct-Tie Rig/configuration context.
















If a Fish has no defensible ordinary `FISH_RIG_GUIDANCE` record, omit **Rigs to Start With** rather than showing a misleading empty-state message. Specialized-targeting guidance remains separately owned. Exact row shell, separators, spacing, typography, wrapping, and responsive geometry remain build-review refinements.








### Fish Compare Similar Fish supporting-navigation structure — checkpoint 154.5








Checkpoint 154.5 is **APPROVED / refinement allowed**. **Compare Similar Fish →** remains a direct ABOUT THIS FISH navigation/workflow row and is not an expander. Remove the existing comparison thumbnails/tiles from the normal Fish Detail page; pair imagery and pairwise distinctions belong to the comparison workflow.








The Fish-detail row may include one compact secondary line listing the approved related Fish names. The complete row is one navigation target; those names are informational context rather than nested links.








Destination behavior is relationship-count aware:
- exactly **one** approved active comparison partner → open that pair comparison directly;
- **two or more** approved active comparison partners → open a current-Fish-scoped comparison chooser that contains only valid `FISH_IDENTIFICATION_RELATIONSHIPS` involving the current Fish;
- **zero** approved active comparison partners → omit the Compare Similar Fish row entirely rather than showing an empty state.








The scoped chooser uses a stable neutral order, preferably alphabetical by related Fish common name. Do not silently rank comparison partners because the identification relationships are unordered/bidirectional and carry no priority semantics.








The global Fish Guide **Compare Similar Fish** catalog remains a separate complete-library workflow. Detail-origin navigation preserves current Fish context: Parent from a directly opened pair returns to the Fish Detail; when a scoped chooser was required, Parent from the pair returns to that chooser and Parent from the chooser returns to the originating Fish Detail. Exact chooser-card geometry, media size, spacing, and responsive treatment remain build-review refinements.




### Fish exceptional/supporting states — checkpoint 154.6




Checkpoint 154.6 is **APPROVED / refinement allowed**.




Material **Safety & Handling** information remains visibly presented and is not hidden solely inside an expander. Safety is semantically independent of specialized-targeting guidance; the current `specializedTargeting.safety` implementation is not promoted into a universal Fish safety schema by this checkpoint. Exact warning iconography, border/surface treatment, spacing, and responsive geometry remain build-review refinements.




For explicitly authored exceptional targeting guidance, use the beginner-facing **Fishing This Species** independent expander rather than the implementation-oriented label **Specialized Targeting**. This expander appears only when explicit specialized guidance exists. Absence of ordinary `FISH_RIG_GUIDANCE` does not automatically create it, and ordinary Rig guidance plus exceptional targeting remain independently derived.




Inside **Fishing This Species**, retain a concise beginner-facing explanation of why the species may require methods outside FCC's ordinary Rig library. Replace the current raw **Try searching for...** query list with a compact **Learn More** action group:
- **Tackle & Equipment ↗** may launch a preconstructed external research/search destination;
- **Methods & Techniques ↗** may launch a preconstructed external research/search destination;
- **Fishing Regulations →** routes through FCC's existing Regulations experience when regulation checking is materially relevant.




Do not require the user to copy raw search strings. The underlying external provider, exact query construction, and later replacement by curated/internal FCC knowledge remain implementation/refinement details. External research actions use the established `↗` grammar; FCC-internal Regulations navigation uses `→`.




Optional absence defaults to clean omission rather than generic empty-state copy. Omit aliases, empty Habitat subgroups, Rigs to Start With, Fishing This Species, Compare Similar Fish, Safety & Handling, or optional secondary metadata when their applicable canonical/explicit content is absent. This omission rule does not apply to required Fish production content: missing required identity, primary identification media, summary/identification material, or other required production dependencies is a validation/data defect rather than a normal presentation omission.


### Fish Detail interaction + responsive finalization — checkpoint 154.7


Checkpoint 154.7 is **APPROVED / refinement allowed** and closes the Fish Detail discussion baseline before implementation review.


Use one compact **ABOUT THIS FISH** grouped disclosure shell rather than separate outer cards for each supporting section. Applicable rows include **Key Identification Traits**, **Habitat & Water**, **Rigs to Start With**, **Fishing This Species**, and the direct-navigation **Compare Similar Fish →** row. Each disclosure remains independent; opening one does not close siblings. The complete disclosure row is one actionable target with at least the shared 48px target height, clear focus-visible treatment, programmatic expanded/collapsed state, and a programmatic relationship to its panel. Enter and Space toggle the disclosure. The visual `▾ / ▴` cue is excluded from the accessible name and may align at the trailing edge because it communicates state rather than directional navigation. Collapsed panel content is removed from keyboard interaction. Do not add exclusive-accordion arrow-key behavior.


Fresh Fish-detail entry starts applicable supporting disclosures collapsed. During a detail visit, disclosure state is transient navigation/session context. When the user leaves Fish Detail for a related internal destination and uses **Parent** to return, restore the originating Fish, Fish-detail scroll position, and prior disclosure states. Home clears contextual return state; selecting another Fish or freshly entering the same Fish later uses the normal collapsed defaults. Do not persist disclosure state as User Knowledge, Preferences, or long-lived local state.


Contextual knowledge controls inside expanded content remain their own single targets. Closing contextual information restores keyboard focus to the originating trigger. Do not create nested interactive controls inside one knowledge chip.


Responsive behavior:
- **mobile / narrow:** Fish Detail remains fundamentally one column; disclosures stack vertically and expanded content stays in normal document flow;

### Fish pair-comparison page — checkpoint 155.3

Checkpoint 155.3 is **APPROVED / refinement allowed**. The pair-comparison page remains a focused field-identification surface owned by `FISH_IDENTIFICATION_RELATIONSHIPS`, not a duplicate Fish-detail page.

Use the hierarchy **FIELD IDENTIFICATION → Fish A vs Fish B → concise comparison guidance → comparison media → comparison facts/actions**. Scientific names, category, Family, aliases, summaries, Habitat, Rig guidance, and other non-identification metadata are omitted from this page. Pairwise distinction statements are rendered from the canonical relationship as authored; do not infer or manufacture trait-by-trait comparison rows that the relationship data does not explicitly encode.

Responsive presentation has two intentional modes:

- **two-column comparison mode:** when both Fish images remain diagnostically useful at the available width, keep a complete left-to-right comparison. Fish A occupies the left column and Fish B the right. Each column contains Fish name, prominent identification image, a compact **Key Differences** label, that Fish's relationship-owned distinctions, and **View [Fish] →**. The image and fact columns therefore align as one complete visual/factual comparison.
- **stacked comparison mode:** when two columns would shrink the Fish images too far, stack both Fish identification images first as **Fish A name → Fish A image → Fish B name → Fish B image**. After the second image, present all **Key Differences** content for Fish A and Fish B, followed by their respective **View [Fish] →** actions. This intentionally keeps the two Fish images adjacent in the reading flow so the user can compare them with minimal scrolling before reading the detailed facts.

The switch between modes is determined by actual image usefulness/readability during implementation review rather than by assigning an arbitrary breakpoint solely because a common viewport threshold exists. Exact breakpoint, image height, divider treatment, spacing, typography, and narrowest-width behavior remain bounded build-review refinements.

Pair orientation is presentation state only and never changes the unordered/bidirectional relationship model. From Fish Detail or the scoped chooser, the originating Fish appears first/left. From the global catalog, preserve the catalog's deterministic displayed pair orientation. Parent return must preserve the originating path/context rather than silently flipping the comparison.

Use one shared comparison composition rather than treating the two Fish as unrelated independently accented peer cards. `FIELD IDENTIFICATION` may remain a compact task eyebrow, but the page must not rely on a fixed Fish-specific page/subpage color.

No production Fish source/data/media/configuration change is authorized by this approval.

### Fish comparison navigation, context, and interaction — checkpoint 155.4

Checkpoint 155.4 is **APPROVED / refinement allowed**. Compare Similar Fish uses path-preserving contextual navigation rather than one fixed parent destination. Parent follows the actual route by which the current surface was reached; Home exits the comparison workflow and clears its transient comparison-return context.

Approved path behavior:

- **global catalog → pair comparison:** Parent from the pair returns to the global Compare Similar Fish catalog, restoring the prior catalog scroll position and, where practical, focus to the originating comparison card; Parent from the catalog returns to Fish Guide;
- **Fish Detail → direct pair** when exactly one active partner exists: Parent from the pair returns directly to the originating Fish Detail and restores that Fish-detail scroll/disclosure state;

- **pair comparison → View [Fish] → Fish Detail:** the opened Fish Detail treats the pair page as its contextual parent. Parent returns to the same pair comparison, which still retains its own prior parent chain; and

On the pair page, Fish names, images, and comparison columns are not additional Fish-detail navigation targets. Each explicit **View [Fish] →** action is its own navigation target. Global-catalog and scoped-chooser cards remain one whole-card control; their **Compare →** text remains a visual affordance rather than a nested separately focusable action.

Comparison navigation state is transient session/navigation context only. Parent restores relevant prior scroll position and, where practical, keyboard focus to the originating control. If that exact trigger no longer exists, move focus to a sensible surviving page heading/navigation target rather than an invalid node. Do not persist comparison return state as User Knowledge or Preferences.

Use normal document/tab order; do not add special arrow-key grid navigation or a custom comparison keyboard model. Existing practical touch-target and visible-focus requirements continue to apply. Responsive reflow between two-column and stacked comparison presentation changes layout only; it must not change Fish A/Fish B semantic order, navigation order, or focus order.

No production Fish source/data/media/configuration change is authorized by this approval.

# User Knowledge Status / Recovery Surfaces
































































UD-11 defines a cross-cutting exception/status layer for authentication, synchronization, conflict, restore, and recovery state. This is not a separate Version 1 Sync/System/Data Health Settings area.
































































- Healthy authenticated/synchronized operation is intentionally quiet; do not require a permanent global success badge.
- Signed-out use is a normal supported state because Reference Knowledge remains available.
- Authentication uncertainty, confirmed sign-out/loss of authorization, synchronization degradation, and confirmed network-offline state must remain semantically distinct; do not claim a connectivity cause that is not known.
- Temporary authentication/synchronization uncertainty preserves local User Knowledge and must not trigger destructive clearing.
- Material synchronization degradation or accepted local changes waiting to synchronize may use a persistent non-blocking status when the condition is actually known.
- Unsafe semantic conflicts use user-facing language such as **Data needs review**, remain scoped to affected records/domains, and present the actual competing values/change intentions rather than provider/revision/device jargon.
- Restore in progress is a persistent protective state. Restore completion/failure must distinguish pre-replacement failure, failed restore with successful rollback, successful restore, and critical recovery failure. Critical recovery failure blocks ordinary User Knowledge mutation until trustworthy state is re-established.
- A successful full restore must communicate when **What I Have With Me Today** requires explicit reconfirmation.
- Important authentication/sync/conflict/recovery states must not rely solely on transient toasts or color. Use plain-language text, accessible semantics/iconography or equivalent reinforcement, and an appropriate action.
- Profile, Data Management, and affected semantic domains retain their established ownership; status surfaces should link or route to the owning action rather than duplicate it.
































































Exact component styling, banner placement, iconography, ARIA/live-region mechanics, retry behavior, diagnostics, and provider-specific status detection are implementation details subject to validation.
































































# Persistent Navigation Component
































































Every non-Dashboard standard application view uses the shared floating navigation system.
































































The canonical shell is `.page-navigation-group`; renderer-based views should use `buildPageNavigationMarkup()` when practical.
































































- Root section pages use one non-duplicative `← Home` control.
- Nested browse/search/detail pages use `← Parent` + `Home` in the same floating container.

- Specialized workflows may replace the standard group when workflow state genuinely requires it, but should reuse the established floating-container visual language unless an explicit exception is approved.
- Keep navigation keyboard accessible, touch usable, compact, responsive, and non-obscuring.
































































Canonical standard-view transition semantics:
































































```text
Forward
→ newly selected destination starts at top
































































Parent
→ restores the immediately preceding standard application view
→ restores applicable prior UI state
→ restores that view's prior scroll position
































































Home
→ Dashboard starts at top
→ contextual return state is cleared
```
































































A saved scroll position belongs only to the source context being restored; it must never transfer into a newly opened destination.

# Contextual Information and Link Semantics
































































Permanent contextual-information convention:
































































```text
Name ⓘ
```
































































This opens information without leaving the current page; desktop may use a centered modal and mobile may use a bottom sheet. Closing restores focus to the original trigger.
































































Directional/navigation semantics:
































































- external verified destination → `↗`, opens externally, label names destination when practical;
- internal directional navigation → `→` when an arrow cue is appropriate;
- contextual information → `ⓘ`, never an external-navigation marker;
- where a compact knowledge chip itself opens contextual/reference information, make the **whole chip** the target and give it visibly interactive hover/focus/pressed treatment distinct from passive chips; a trailing `ⓘ` may reinforce the behavior but is not a separate target;
- directional glyphs remain immediately adjacent to destination text rather than detached at row edge;
- use native Unicode glyphs rather than CSS-drawn arrows;
- navigation-arrow glyph weight is `800` for established `←`, `→`, `↗`, and compact-row `›`; wrap glyphs separately so label weight need not change.
































































Current production Dashboard **Regulations** is internal navigation to the state gateway. Official state-resource destinations remain external `↗` actions.

The Companion should support keyboard navigation, visible focus, sufficient contrast, descriptive labels, useful alt text, responsive text/layout, and semantics that do not rely on color alone. # Exception Rule
































































A page/component may diverge from this standard only when a real functional, semantic, accessibility, safety, or domain requirement makes the shared treatment inappropriate. Convenience, domain membership, bespoke markup, or implementation history are not sufficient exceptions.
